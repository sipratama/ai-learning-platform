# VS-02A — Go JWT security review and recommendations

Date: 2026-11-01 Asia/Jakarta. Baseline: `91080f45e1aba38316eeecca6eeba3f618bd7f3a`. **Technical recommendations for independent review; no implementation or policy approval.** [VSA-DEC-001](08-po-supabase-hosted-es256-platform-selection-2026-11-01.md) selects hosted Supabase and ES256/P-256 only. This addendum refines [VSA-P1](02-identity-and-authorization-design.md), preserving historical proposals and identifying implementation traps.

## 1. Dependency recommendation

Recommend **`github.com/golang-jwt/jwt/v5 v5.3.1`**, subject to the O04 specialist disposition and fresh vulnerability review when implementation is authorized. Its [maintainer release](https://github.com/golang-jwt/jwt/releases/tag/v5.3.1) provides evidence of maintenance. The [tagged module](https://github.com/golang-jwt/jwt/blob/v5.3.1/go.mod) declares Go **1.21** with no external module requirements; this fits the repository's `go 1.27` / CI Go **1.27.3**. An isolated `go list -m -json ...@v5.3.1` resolved the exact version and upstream SHA `7ceae619e739dc8a7bf577214aa8ebf26668e9db`. This verifies resolution/minimum-version compatibility, not compilation, verifier correctness or a clean vulnerability scan. No dependency was added to the application.

The [ECDSA implementation](https://github.com/golang-jwt/jwt/blob/v5.3.1/ecdsa.go) supports ES256 and delegates cryptography to Go. The library supplies signature/claim parsing, not remote JWKS lifecycle or full application policy. Keep a small fixed-trust transport/key adapter around the library; do not implement signature mathematics. A second automatic remote-key library would introduce cache/default behavior that also needs review. Selection is a recommendation, not an approved pin.

Map [parser options](https://github.com/golang-jwt/jwt/blob/v5.3.1/parser_option.go) deliberately: `WithValidMethods` allowing only ES256; `WithIssuer`; `WithAudience`; `WithExpirationRequired`; `WithIssuedAt`; `WithLeeway`; `WithStrictDecoding`; and an injected clock in deterministic tests. Never use `ParseUnverified`, `WithoutClaimsValidation` or unsigned acceptance for authentication. Require both successful parsing/validation and a valid token; do not continue based on partial error classifications.

Additional checks remain essential: audience options check membership rather than forbidding extra audiences; issued-at validation does not itself require `iat`; strict base64 decoding does not reject duplicate JSON members. Use strict bounded preprocessing and typed/custom claim validation for those policies. Require integral seconds, required typed claims, canonical UUIDs, no duplicate/null/ambiguous claims, singleton exact audience and bounded `exp-iat`. See [validator source](https://github.com/golang-jwt/jwt/blob/v5.3.1/validator.go). Tests must cover the actual composed parser, not a decode-only helper.

The [maintainer advisory index](https://github.com/golang-jwt/jwt/security/advisories) lists historical parsing allocation and error-handling issues. [GHSA-mh63-6h87-95cp](https://github.com/golang-jwt/jwt/security/advisories/GHSA-mh63-6h87-95cp) affects v5 through 5.2.1 and is patched in 5.2.2; recommended 5.3.1 is outside that published affected range. [GHSA-29wx-vh33-7x7r](https://github.com/golang-jwt/jwt/security/advisories/GHSA-29wx-vh33-7x7r) applies to v4 through 4.5.0, with the fix backported from v5. This bounded advisory review does not replace checking current Go advisories against the final resolved module graph. Pin the reviewed version and checksum in the future implementation PR, retain dependency-scan evidence, and reassess if the selected version changes.

## 2. Proposed verification and failure profile

All numeric values below remain **recommended**, inherited from VSA-P1, not PO SLAs or observed tenant configuration.

| Concern | Recommended behavior / acceptance evidence |
|---|---|
| Algorithm/key type | Explicit ES256 allowlist and expected ES256 method; trusted `*ecdsa.PublicKey` on P-256 only. Reject HS256, RS256, `none`, encrypted/symmetric/private/malformed keys, unsupported `crit`/extensions and key confusion. No algorithm negotiation from JWT input. VSA-T02–T04. |
| Trust context | One immutable out-of-band exact HTTPS issuer. Derive only its well-known JWKS URL; reject redirects and JWT `jku`/`x5u`/`jwk` trust. Exact configured audience as string or singleton array; reject missing, duplicate/extra or wrong audiences even if library membership validation succeeds. VSA-T05/T27. |
| Required claims | Require verified `iss`, `aud`, canonical UUID `sub` and `session_id`, integral `iat` and `exp`. Validate optional `nbf`. Require provider user context `role=authenticated`; deny anonymous/service/API credentials. Provider role/metadata never grants Student/Admin. VSA-T04–T06/T14. |
| Time | Proposed skew **30 s**, maximum **3600 s** issued lifetime, token **8192 bytes**, kid **128 bytes**. Require `iat < exp`, `0 < exp-iat <= 3600`, `iat <= now+30`, `now < exp+30`, and optional `nbf <= now+30` and `nbf < exp`. Expiry equality rejects. Require a trustworthy synchronized clock, never widen skew during drift. VSA-T06. |
| JWKS ingestion | TLS verification, no redirects, total Go fetch deadline **2 s**, response **64 KiB** / **8 keys**; reject private/unsupported keys, duplicate kids/members, invalid points and incompatible optional metadata. Parse/validate the complete replacement before atomic publication. Public metadata probe is not this verifier. VSA-T03/T08/T10. |
| Cache | One bounded cache per configured issuer; **5 min hard TTL**, refresh at **4 min**, monotonic age from last successful fetch. No stale-after-expiry trust. Failure never resets success age. Public Guest liveness remains independent of identity readiness. VSA-T07/T08. |
| Refresh concurrency | One in-flight fetch per issuer, shared bounded wait/deadline, cancellation and bounded waiters; issuer-wide unknown-kid refresh cooldown **30 s**, no attacker-controlled per-kid cache/map. Bound negative results to the current set/cooldown. Routine refresh also respects bounded concurrency. VSA-T10/T29. |
| Unknown kid | Fresh complete set lacking kid: 401. At most one controlled refresh when eligible; on cooldown with a fresh authoritative set, return 401 without refetch. If no usable authoritative set or attempted required refresh fails: 503. Never try every key or trust embedded URLs. VSA-T07/T08/T10. |
| Outage | Fresh known trusted key may verify until hard TTL; cold/expired/unusable set gives 503, never fallback credentials or stale trust. Unknown key in a successfully fetched set gives 401. Distinguish malformed credentials (401) from operational inability to establish trust (503). VSA-T08/T21. |
| Rotation/revocation | Observe standby propagation before switch; test overlap/removal in separately authorized isolated drill. Issuer+kid emergency denylist overrides all cached trust, or disable identity traffic. Purging Go cache cannot bypass provider edge caching. VSA-T07. |
| Malformed JWT | Bound input before decoding; exactly three compact segments; reject duplicate headers/JSON members, invalid base64/trailing data, unsupported types, excess sizes and critical extensions; safe generic 401 with no parser detail, panic or Account lookup. Fuzz composed ingress and parser after authorization. VSA-T02/T04/T23. |
| Server authority | After verification, current PostgreSQL binding, ACTIVE state and Go-owned grants on every protected request; no positive role/state cache. Missing/restricted/roleless = generic 403, DB unavailable = 503. Transaction-aware state/grant recheck for commands; no GET provisioning. VSA-T11–T16/T20–T22. |

Supabase's [signing-key guide](https://supabase.com/docs/guides/auth/signing-keys) documents EC/P-256 signing and staged key states. A compatible published key can be standby or retained; it does not prove current signing. The [JWT verification guide](https://supabase.com/docs/guides/auth/jwts#verifying-a-jwt-from-supabase) documents the public well-known endpoint, potentially empty sets, ten-minute edge caching and propagation waits of at least twenty minutes around key-state changes. **Inference:** local five-minute TTL alone cannot guarantee emergency revocation in five minutes; independent containment and actual provider rotation evidence are required.

## 3. O05 — logout and live validation decision

Supabase [sign-out documentation](https://supabase.com/docs/guides/auth/signout) states that affected refresh credentials are removed while issued access tokens can remain usable until expiry. SDK default logout scope is global; if local-session logout is intended, the scope must be chosen explicitly and tested. Browser clearing is not server revocation.

| Candidate requiring PO + security approval | Security implication | Required change / proof |
|---|---|---|
| Provider-only logout + offline access verification | A stolen previously issued JWT can replay against an ACTIVE Account until `exp + skew`; with the proposed lifetime this is at most **3630 s from issuance**, not necessarily from logout. Removing local browser state does not stop another bearer holder. Refresh failure must prevent renewal. | Explicitly accept the bounded replay risk and logout scope for the synthetic proof; measure actual VSA-T09 token replay and expiry. Do not label ST-003 immediate session revocation PASS. Consider a shorter supported TTL only with explicit review. |
| Signature/claims plus live session authority | Deny a valid JWT once its verified session no longer exists; adds a synchronous dependency, latency, schema/capability design and outage behavior. A positive session cache reintroduces a replay window. | Review a narrow server-only lookup bound to verified issuer, `session_id` and `sub`; no browser/general Auth schema access, no call while holding business DB locks, no positive cache where immediate invalidation is promised. Missing session = 401; authority outage = 503. Define transaction/race boundary: an already-authorized request can finish after logout. Verify provider timeout, ban/delete and removal behavior empirically. |

The [sessions guide](https://supabase.com/docs/guides/auth/sessions#how-to-ensure-an-access-token-jwt-cannot-be-used-after-a-user-signs-out) explains correlating `session_id` with `auth.sessions` to detect sign-out. Neither an offline verifier nor an unproven `/user`/`getUser` call establishes live session existence. Provider session limits and ban/delete behavior need actual tenant evidence, not assumptions. Local Account restriction remains independently mandatory for either option; it denies all of that Account's tokens on the next protected check.

**Recommendation:** keep both options open for accountable review. Do not infer replay acceptance from selecting ES256, synthetic-only operation or memory-only storage. Admin session/MFA/recovery assurance belongs to O09 and is excluded from Bundle 1. O04 and O05 remain open until the named reviewer/PO signs the exact profile and policy.
