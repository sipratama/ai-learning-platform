## 2. Hosted test project versus local Supabase

Supabase documents a CLI plus Docker-compatible runtime for its local stack, which runs multiple services and is intended for development. [Supabase local development](https://supabase.com/docs/guides/local-development). This is different from the repository's current two-container Guest preview; it would require installation/configuration and operational ownership. Local stack signing defaults must be inspected, not assumed to match hosted ES256.

| Option | Benefits | Costs and limitations | Proposed use |
|---|---|---|---|
| Dedicated hosted Supabase test project | Closest evidence for managed Auth issuer, actual signing/JWKS propagation, SDK refresh/logout and hosted Data API grants; lower local service maintenance | Internet/provider availability, project ownership/cost, credential custody, shared-state races and rate/email limits; rotation/deletion tests can disrupt others | **Recommended initial real-provider integration**, after PO/operator approves project and synthetic-only use. Use a disposable second test project or approved isolated rotation window if shared users would be affected |
| Isolated local Supabase stack | Offline/resettable provider+DB, synthetic accounts, deterministic fault injection and easier destructive experiments | More services/resources, local credentials/signing/issuer/TLS configuration, local-vs-host networking and possible hosted behavior differences; local JWT_SECRET/HS256 setups fail VSA-P1 | Optional later if repeatable provider resets or CI needs justify it; separately authorize installation/configuration. It cannot replace hosted-specific propagation evidence |
| Local verifier/JWKS fake + disposable PostgreSQL | Fast deterministic invalid-token/time/key/outage and real constraint/concurrency tests; no hosted project for routine tests | Does not prove Supabase authentication, actual session semantics, managed key caches or browser integration | Required deterministic base layer, combined with actual-provider evidence; no deployable token bypass |

Select the hosted-project route provisionally for planning, not as an approved purchase or created resource. Operator must supply project authority, approved region, synthetic identifiers, signing evidence, DB privileges, redirect/origin allowlists, cleanup/reset scope, credential rotation and test budget/rate constraints before dependent work. Singapore remains only a conditional preference under FA-008; neither location nor paid tier is selected here. No production user copy or production credential is acceptable.

Proposed secret handling: browser sees only the public project URL/publishable key; API sees private DB runtime credentials; migrator/provisioner/bootstrap each use separately scoped operator credentials. Any provider admin key needed for synthetic account preparation belongs only to an approved nonpublic operator process, never React, build arguments, image layers, Go request logs or ordinary API configuration. Do not install a service-role key simply to perform JWKS verification. Secret examples contain variable names/placeholders only; actual secret-store setup and test accounts require later authorization.

Identity browser/network evidence must verify no direct core-data CRUD or privileged key. Review default proxy access/error logs before auth flows; no token/credential/query-bearing URLs, authorization headers, passwords or session payloads in logs. Test traces/videos/screenshots around login can contain credentials and must be disabled or sanitized before retention. No public debug endpoint prints configuration or decoded JWTs.

## 4. Candidate verification execution plan

No commands below are claimed run for identity. After authorization, use repository-pinned Go/Node versions and lockfiles. Retain current standard/tagged Go vet/test/race/build and fixture-boundary checks, frontend typecheck/lint/Vitest/build, mocked UI and real-Go Guest Playwright. Add distinct identity test targets rather than redirecting Guest fixtures into real Auth.

1. Deterministic verifier/use-case tests: generated ephemeral test keys, injected clocks/HTTP transport, strict profile and no bypass header. Run Go race tests for process/cache safety.
2. Disposable PostgreSQL integration: migrate isolated empty database, verify grants/constraints, concurrent provisioning/bootstrap/restriction barriers, fault/unknown-commit and migration/application rollback. Refuse any non-test DSN/config fingerprint. No production data restore.
3. Actual Supabase provider contract: approved synthetic users, real ES256 tokens and issuer/audience, metadata tamper, key rotation/outage/replay/refresh observations. Separate authorization for disruptive provider actions; store redacted public configuration and results only.
4. React component plus actual Auth→Go→DB browser E2E: no product endpoint interception for real flow; storage/logout/race and error cases; unchanged Guest preview without credentials; both desktop/mobile and manual new-form accessibility observations.
5. Candidate CI: preserve existing jobs; add secret-gated provider job only in trusted workflow context with no secrets on untrusted fork PRs, minimum permissions and no deploy credential. Offline/P tests remain required independently. A skipped provider job is NOT RUN, not success. Record source/artifact/config identity, locked dependencies and security review.

Applicable identity tests must pass before DD-001/QUAL-003 review; exact-candidate evidence and independent human reviewer dispositions are necessary. QUAL-004 merge, QUAL-005 deployment and QUAL-006 beta remain separate decisions. Real-data use cannot start before VS-06A cleanup/retention/restore proof. Do not run beta workload or production disruption merely because this plan lists tests.
