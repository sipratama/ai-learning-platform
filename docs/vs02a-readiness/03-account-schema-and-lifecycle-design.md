## 1. Proposed tables and constraints

Use a private, unexposed schema such as `identity`, with module-owned tables. Go generates random UUIDs; UUIDs are opaque identifiers, not authorization. All times are `timestamptz`, server-issued and returned with explicit UTC offset. Do not copy passwords, refresh tokens, raw access JWTs, emails or mutable profile JSON into these records.

| Table / logical owner | Proposed columns and keys | Integrity, indexes and privileges |
|---|---|---|
| `account` / MOD-001, ENT-001 | `account_id uuid PRIMARY KEY`; `created_at timestamptz NOT NULL`; `updated_at timestamptz NOT NULL` | Stable internal identity, no email-derived key. Ordinary API has SELECT only for this slice. Future owner tables reference this ID with explicit deletion policy; no broad cascades. |
| `external_identity` / MOD-001 | `binding_id uuid PRIMARY KEY`; `account_id uuid NOT NULL REFERENCES account ON DELETE RESTRICT`; `issuer text COLLATE "C" NOT NULL`; `subject uuid NOT NULL`; `created_at timestamptz NOT NULL` | `UNIQUE(issuer, subject)` across **all** retained states, not just ACTIVE; `UNIQUE(account_id)` for one binding per Account in this increment. Issuer canonicalized only against configured exact value, not generic URL rewriting. No email linking, mutable subject or account rebinding. API read only; provisioner narrowly inserts. |
| `account_access` / MOD-001 | `account_id uuid PRIMARY KEY REFERENCES account ON DELETE RESTRICT`; `state text NOT NULL`; `revision bigint NOT NULL DEFAULT 1`; `changed_at timestamptz NOT NULL`; `reason_code text NOT NULL` | `CHECK state IN ('ACTIVE','SUSPENDED','DELETION_RESTRICTED','DELETED')`; positive revision; allowlisted nonpersonal reasons, no free-text notes. One row required per Account by atomic creation and integrity checks; missing row denies. Proposed SUSPENDED semantics need VSA-O08 approval. API read only; narrow authorized status capability changes state/revision. |
| `role_assignment` / MOD-001, ENT-002 | `(account_id uuid, role_code text) PRIMARY KEY`; `account_id REFERENCES account ON DELETE RESTRICT`; `role_code CHECK IN ('Student','Admin')`; `grant_operation_id uuid NOT NULL UNIQUE`; `granted_at timestamptz NOT NULL` | At most one grant per role/Account. Grant operations audited; no browser/DML API. Provisioning capability can grant only Student; separate bootstrap capability grants Admin. No implicit role hierarchy/claim import. Role revocation removes the current grant in an authorized audited transaction; durable event records its effect. |
| `identity_operation` / MOD-001 | `operation_id uuid PRIMARY KEY`; `operation_kind text NOT NULL`; `payload_fingerprint bytea NOT NULL`; `account_id uuid REFERENCES account ON DELETE RESTRICT`; `completed_at timestamptz NOT NULL` | Unique idempotency identity for nonpublic provision/state/bootstrap operations; fingerprint covers canonical environment, issuer, subject, action and requested transition. Conflict with a different payload is denied. Never fingerprint passwords/tokens. Linkability is personal data; minimize/remove later under FA-006, not keep forever. |
| `bootstrap_control` / MOD-001 | `environment_id text PRIMARY KEY`; `consumed boolean NOT NULL`; `completed_operation_id uuid UNIQUE NULL`; `completed_at timestamptz NULL` | Migrator creates exactly the environment's sentinel row, initially unconsumed. CHECK consumed iff completion fields present. Immutable completed marker through narrowly scoped command; no API write grant. Do not delete/reinitialize on API restart or when Admin leaves. Minimized historical operation proof survives role removal without requiring indefinite subject retention. |
| `security_audit_event` / MOD-011, ENT-026 | `event_id uuid PRIMARY KEY`; `action_id uuid NOT NULL`; `event_type text NOT NULL`; `outcome text NOT NULL`; `occurred_at timestamptz NOT NULL`; `request_id text NULL`; `environment_id text NOT NULL`; `reason_code text NOT NULL` | `UNIQUE(action_id,event_type)` for one canonical durable action event; allowlisted event/outcome/reason, validated request ID. Index `occurred_at` for expiry and `(event_type,occurred_at)` for investigation. No unbounded JSON payload, raw identity/role claims, URL, IP, user agent, SQL or secret. API has narrow append capability where needed, no UPDATE/DELETE or general read. |
| `audit_accountability_link` / MOD-011 | `event_id uuid PRIMARY KEY REFERENCES security_audit_event ON DELETE RESTRICT`; optional `actor_account_id`, `target_account_id` FKs to Account with explicit restriction; approved operator reference if required | Separate protected **linkable** mapping for accountability, not anonymous evidence. Least-privilege reviewer access only. Remove/minimize mappings under approved privacy policy before Account erasure; no audit row stores identity in a hidden free-text field. Exact mapping lifetime/allowed operator references require VSA-O10. |

`role_assignment.grant_operation_id` should reference `identity_operation.operation_id` through a foreign key; operations are inserted first within the same transaction. Bootstrap completion links the same operation. Future cleanup must remove role/operation/accountability links in the reviewed order before personal Account removal; no default `CASCADE` encodes an unapproved erasure policy. Security audit action UUID is a correlation key, not necessarily a permanent FK to personal operation records. Missing/disagreeing environment control blocks privileged operations.

Store core tables outside exposed Supabase Data API schemas and revoke all `anon`/`authenticated` table/function access. If any exposed-schema placement is selected, enable RLS with no browser policies plus explicit grants/revokes and test it; do not rely on hiding table names. Ordinary Go connection must not be `postgres`, table owner, `service_role` or BYPASSRLS. Migration/schema owner is separate; bootstrap/provisioning capabilities are separately scoped, ideally narrowly reviewed DB functions with fixed search path, qualified relations, validated arguments and PUBLIC execute revoked. Avoid broad SECURITY DEFINER helpers. No direct FK into managed `auth.users` is proposed: trusted issuer/subject binding and controlled reconciliation remain explicit across provider boundaries.

## 2. Provisioning and identity binding

**Proposed initial approach:** pre-create synthetic Auth users only in an authorized environment, then run a trusted nonpublic internal provisioning operation. Auth user creation and Account provisioning are separate, so retries never create another provider user. The operator verifies the exact configured project and known provider user through trusted provider evidence; a random UUID supplied by a browser is insufficient. The API runtime needs no provider admin credential.

Account provisioning transaction creates Account, ACTIVE access row, one issuer/subject binding, Student assignment, operation record and minimized audit atomically. No Admin assignment occurs. Existing matching binding returns the same Account only if the operation is authorized and current state allows the requested idempotent outcome; it never resets state or restores roles. Same operation/different identity is a conflict. An existing restricted/deleted binding denies reprovisioning. A missing Account at API-006 returns generic 403, rather than a new identity. Separate reviewed onboarding/signup is required to change this design.

Multiple identity providers, merging users by email, account linking/unlinking, subject recycling, signup invitation policies and self-service recovery are excluded. A new provider user with the same email receives no old Account or Admin role. Different trusted issuers with the same UUID must not collide; each integration database is also environment-isolated. Configuring several issuers in one process is not in VSA-P1.

## 3. Transactions and concurrency

PostgreSQL unique indexes provide the final uniqueness arbiter. At Read Committed, `ON CONFLICT DO NOTHING` can lose to a concurrent insert that was not visible to the statement snapshot; do not assume that statement also returns the winning row. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED).

| Operation | Proposed transaction / locking protocol | Unknown outcome and failure |
|---|---|---|
| Provision identity | Begin; check operation key/fingerprint; read existing binding; if absent create candidate Account + access + binding + Student grant + operation/audit together. Unique collision rolls back the **whole candidate** including Account. Start a fresh transaction/snapshot, resolve winner and verify invariants; bounded retry only for classified conflicts. No unbound orphan survives. | Read by operation ID and issuer/subject after timeout; return recorded Account, never blindly create. Inject collision/audit failure/serialization/deadlock cases against actual PostgreSQL. |
| API-006 | Read binding, Account/access and roles in one consistent read transaction/snapshot. Require ACTIVE and nonempty authorized roles. Serialize only minimal fields; never expose intermediate provisioning. | Concurrent restriction may linearize after this read; a response authorized before restriction can finish afterward. Every subsequent protected request rechecks. An absolute “retract bytes already sent” guarantee is not made. DB failure yields 503. |
| Protected command guard | Owning use case locks Account then `account_access` (exclusive row lock proposed for small initial volume), reads current grants and enforces permission/owner in the command transaction. All role/state changes follow the same Account-before-access lock order. Keep lock until command commit. No external provider call while holding these locks. | If restriction commits first, command denies; if command commits first, restriction follows it. No new protected command can commit on a stale ACTIVE snapshot after accepted restriction. Test with barriers, not timing sleeps alone. |
| Access restriction | Authorized internal owner capability locks Account/access, checks expected revision/current state, changes state+revision, records operation+required audit in one transaction. No public suspension/deletion endpoint is added. | Missing audit rolls back; provider outage cannot reactivate Account. Same operation replay returns prior outcome only through trusted access; stale/conflicting transition denies. |
| Initial bootstrap / TX-020 | Lock environment sentinel first, then Account/access; current state and existing grants checked; insert operation, Admin assignment, access revision, event and consumed sentinel in one local transaction. Two subjects cannot consume the same environment marker. | Same intent reads recorded effect; changed subject denied. Missing sentinel/authority/audit fails. A replay after Admin revocation/restriction does not restore the role. |
| Role revocation | Future authorized role-maintenance capability follows Account/access locks, removes grant, increments revision, writes audit atomically; no public role management in this increment. | Concurrent command checks serialized authority; stale JWT role cannot restore grant. Further Admin additions require a separate policy. |

Use parameterized SQL, context deadlines and a bounded transaction retry policy selected/tested under VSA-O07. A transaction retry never repeats an external Auth side effect. Role/provisioning/state mutations do not run on startup automatically. Domain ports own decisions; cross-module callers use owner capabilities rather than direct table writes. This schema does not allocate a fictitious existing TX number to provisioning: TX-016 remains deletion acceptance owned by MOD-010, TX-018 audit, and TX-020 bootstrap in the [transaction register](../DP-03/05-consistency-and-transaction-design.md#1-critical-operation-contracts).

## 4. Access states and deletion boundary

Account authorization state is distinct from provider session state, role and MOD-010 cleanup case state.

| Proposed access state | Protected behavior | Permitted transition / authority |
|---|---|---|
| Missing binding/Account/access row | Generic 403 for valid token; no automatic creation | Only explicit trusted provisioning of a new eligible synthetic identity; corrupt partial rows require operator investigation |
| ACTIVE | Valid user token + current role + owner policy may proceed | Trusted restriction capability may suspend; future MOD-010 acceptance may restrict for deletion |
| SUSPENDED | All protected reads/commands denied 403; public Guest reads remain available | Proposed reversible administrative restriction, only by separately authorized operator with expected revision/audit. Precise authority/reasons/reinstatement require VSA-O08; unknown/undecided states deny |
| DELETION_RESTRICTED | All protected access denied, including API-006, even with unexpired token/Admin role | Maps to accepted restricted/cleanup pending phases. No user login, refresh, retry or operator “unsuspend” returns it to ACTIVE |
| DELETED | All protected access denied; no self-service recovery/reprovisioning | Represents completed lifecycle only after future MOD-010 verifies cleanup; VS-02A tests may seed this synthetic state but must not mark real erasure complete |
| Unknown/corrupt state | Deny; safe operational failure and alert | Repair requires reviewed operator action, never fallback to ACTIVE |

The [FA-006 lifecycle](../DP-03/04-data-lifecycle-and-retention.md#1-account-lifecycle-and-deadline) has ACTIVE → ACCEPTED_RESTRICTED → CLEANUP_PENDING → COMPLETED. The proposed access projection collapses the middle two into DELETION_RESTRICTED; it does not replace the case state machine. Once deletion starts effectively, no self-service recovery is allowed. Suspension must not serve as an escape from this invariant.

VS-02A provides a transaction-aware restriction capability and synthetic tests. **It does not expose API-036, accept real deletion requests, start deletion clocks, delete provider users, execute cleanup, or claim restore compliance.** VS-06A later accepts the valid own request and atomically creates case + restriction + audit/work obligation (TX-016). The original valid-request time starts the approved 30-day active-data clock; retries cannot reset it. Cleanup and reconciliation remain TX-017. No Admin role bypasses the guard.

## 5. Audit and observability persistence

Required durable events in this slice: explicit Account provision outcome, initial Admin grant, authorized access restriction/reinstatement where approved, and role changes within authorized scope. Event contains only bounded type/outcome/reason, time, operation and correlation IDs; protected mapping supports accountability. No raw subject, email, request body or bearer in standard logs. Rejected authentication gets bounded structured telemetry/metrics, not an unbounded personal-event archive for each malicious token.

Runtime cannot alter/delete audit; retention executor and reviewer are separate least-privilege roles. Daily expiry execution and simulated-age tests are proposed for the 180-day security-audit target, subject to approved legal exceptions and VSA-O10 policy. A legal hold must be attributable and scoped; an operator flag cannot silently mean indefinite retention. Linked records/metadata/exports share policy controls. Evidence must demonstrate event capture, mutation denial, read scoping and expiry; a configured retention job is not executed proof.

Audit failure blocks a grant or restricted-state mutation that requires atomic audit. Logging/metric transport failure must not convert failed authentication into success or expose a fallback payload; alert on lost telemetry. Do not block safe Guest reads merely because identity audit storage is offline.

## 6. Migration, rollback and restore plan

Follow [DEL-018–021](../DP-06/04-secure-delivery-and-change-management.md#5-schema-data-migration-and-rollback-boundary). Candidate initial migration is additive: create private schema, tables/checks/indexes, restricted privileges and environment sentinel; no application deployment or real rows are authorized by this document. Review exact SQL later with data/security specialists. Existing baseline has no Account data to backfill. UUID uniqueness indexes/foreign keys are created on empty tables; later backfills and online index construction require their own size/lock analysis. Verify every migration's actual transaction semantics and failure behavior against the selected PostgreSQL version.

Sequence after explicit authorization: validate isolated target/environment fingerprint → migrate empty schema → assert grants/RLS boundary → run constraint/rollback tests → provision only synthetic identities → run bootstrap under its separate authorization → enable identity UI for that environment. API must reject a missing/incompatible schema without auto-migration. Version compatibility checks cover current and previous application artifacts; Guest-only previous artifact must not accidentally expose new tables or activate identity via default configuration.

Preferred application rollback disables identity mode/returns to the compatible Guest artifact while preserving schema and audit. Roll back a failed initial migration transaction on an empty disposable DB; after any grants or evidence exist, do not use a destructive down migration to erase audit/identity history. Use reviewed forward repair or discard the explicitly disposable synthetic environment under its authorization. A routine app rollback must preserve consumed bootstrap state and restrictions. Neither dropping a table nor restoring an old backup is an Admin recovery policy.

Real deletion/restore interactions remain VS-06A prerequisites: expiry inventories, protected suppression/replay, provider/DB/Storage reconciliation and isolated restore before traffic. Retained external bindings and accountability links are **personal while linkable**, not an approved permanent tombstone. Removing them must not allow stale JWTs, re-used provider identities, restored ACTIVE rows or bootstrap resets to recreate access. Explicit provisioning and missing-account denial reduce this risk, but do not prove restored-database safety. The [approved FA-006/B1 policy](../DP-01/04-open-decisions-register.md#4-fa-006--data-retention--account-deletion-parameters) requires active-data deletion within 30 days, backup expiry within 30 days and minimized security audit for 180 days unless legitimate legal obligation; no indefinite suppression identifier, recovery window or irreversible disposition per data class is invented here.

Before real data, VSA-O11 must approve how the VS-06A suppression mechanism is minimized, retained and retired after all replay sources expire. Until then, use synthetic state only; restoration occurs offline/restricted and is not reported as passed. A DELETED flag by itself never constitutes deletion completion.
