## 1. Assets, boundaries and threat assessment

Protect identity authenticity, internal owner binding, Admin authority, lifecycle restrictions, minimized audit integrity, provider/DB credentials and Guest availability. Boundaries are browser → Supabase Auth, browser → Go bearer ingress, Go → fixed JWKS origin, Go → private PostgreSQL authority, and nonpublic operator → provisioning/bootstrap/state capability. Docker build/runtime and CI/evidence storage are additional credential boundaries. React route guards and CORS do not establish server authority.

Risk labels below describe potential consequence, not discovered exploitable defects. “Hard” blocks acceptance if the control fails. “Design gate” requires disposition before implementing dependent code. Sources: [SEC control matrix](../DP-04/02-authentication-authorization-and-security.md#2-control-matrix), [DP-05 ST cases](../DP-05/03-security-privacy-and-abuse-verification.md#2-negative-test-matrix), [hard gates](../DP-05/05-release-evidence-and-go-no-go-criteria.md#3-hard-gates-nonwaivable-through-ordinary-exceptions).

|---|---|---|---|

## 2. Synthetic fixtures and evidence contract

Proposed fixture version **`vs02a-identity-proof@1.0.0`**, not created or seeded. `A`, `B`, `C` are synthetic provider user UUIDs `11111111-1111-4111-8111-111111111111`, `22222222-2222-4222-8222-222222222222`, `33333333-3333-4333-8333-333333333333`; internal Account UUIDs are different. A/B have Student; C initially Student and is the known bootstrap target. No real emails or credentials are supplied here.

`L` means deterministic local verifier/JWKS fake, generated ephemeral signing material inside the future test process, injected clock and provider fault adapter. `P` adds actual isolated PostgreSQL at the selected version; Go's `-race` does not test database uniqueness or isolation. `S` requires an approved **actual Supabase test environment** and real issued tokens for synthetic users (a local Supabase stack is eligible only after its signing/issuer configuration is reviewed). `R` means React/Vitest; `B` means unmocked browser/Go integration. Mocked provider tests cannot substitute for S evidence.

Keys `K1/K2` refer to future ephemeral local signing keys or approved test-project public kids; issuer `I1` and wrong issuer `I2` are distinct configured environments; audience `authenticated`. Synthetic protected owner object `O-B` belongs to B in a **test-only** owner repository; no enrollment/Attempt endpoint/table is added. Account states include ACTIVE, SUSPENDED, DELETION_RESTRICTED, DELETED, absent and corrupt. Bootstrap sentinel starts unconsumed. No fixture is selected by an ordinary request header.

Every future execution records: test and canonical requirement IDs, Git/build/artifact identity, environment/config fingerprint, fixture version, actual UTC time, preconditions, expected/actual status and state, redacted request/response, owner-state before/after, executor/reviewer, artifact checksum/access location, failure/defect and retest links. Allocate DP-05 EVD IDs **only on execution**, under the [evidence contract](../DP-05/01-test-strategy-and-risk-based-coverage.md#5-evidence-contract-and-acceptance-implications). JWTs, passwords, emails, private keys and full browser traces containing credentials must be removed from retained artifacts. Keep failing/repeated runs; do not convert this matrix into a PASS ledger.

## 4. Local verification versus actual provider evidence

Local verifier tests must use the same production verifier interface and algorithm rules with injected transport/clock, not bypass middleware through a “test user” header. P tests use real PostgreSQL transactions and capability grants. Fake keys/network failures enable deterministic negatives but cannot establish actual Supabase issuer/audience, key propagation, logout/session semantics, provider metadata behavior, refresh, bans/deletion or browser SDK behavior.

Actual S evidence is required for VSA-T01/T05/T07–T09/T14/T17/T21–T22/T24–T25/T27/T30–T31 at the boundaries indicated. Auth rotation/destructive session tests must use a separately authorized disposable test project with no shared users or production data. If tenant authority is unavailable, mark S cases BLOCKED/NOT RUN and do not substitute self-issued local tokens. Real-provider capture must be sanitized at collection; browser credential traces are not safe artifacts by default.
